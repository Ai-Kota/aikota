## 一、问题定义

**用户诉求**：不希望看到上下文超限的错误，期望 aikota 能进行"无限"的智能体会话。

**核心问题**：什么是"无限上下文"？技术上如何实现？

## 二、第一性原理分析

### 2.1 根本约束

从物理和信息论角度，任何对话系统面临三个根本约束：

| 约束类型 | 具体表现 | 是否可突破 |
|---------|---------|-----------|
| **模型上下文窗口** | LLM 有最大 token 限制（如 128K, 200K, 1M） | ❌ 不可突破 |
| **信息损失** | 压缩必然丢失细节 | ❌ 不可消除 |
| **计算成本** | 长上下文处理消耗更多时间和费用 | ⚠️ 可优化 |

### 2.2 "无限上下文"的真实含义

**不是**：把整个会话历史一字不漏地传给模型

**而是**：通过智能的信息管理，让模型在每次决策时都能访问到所需的所有必要信息

### 3.2 关键发现：aikota 已经实现了"无限上下文"的骨架

| 组件 | 状态 | 功能 |
|------|------|------|

## 四、配置方案

### 4.1 启用无限上下文模式

修改 `config.toml`：

```toml
# 启用持久化记忆系统
[memory]
enabled = true

# 配置无限上下文检查点
[checkpoint]
# 在哪些上下文使用率阈值时触发压缩
thresholds = ["40%", "60%", "80%"]
# 保留多少 token 给摘要生成
reserved = 8192
# 压缩后保留多少最近上下文
keep_recent = 32000
```

### 4.2 工作原理

```
第1次运行：
  会话开始 → 积累上下文 → 达到40%阈值 → 压缩早期消息 → 写checkpoint
  → 继续会话 → 达到60%阈值 → 再次压缩 → 覆盖checkpoint
  → 继续会话...

第2次运行（续跑同一session）：
  加载checkpoint → 重建上下文（summary + 最近消息）→ 继续会话
  → 积累新上下文 → 再次压缩 → 更新checkpoint
```

**效果**：无论会话多长，每次运行时只加载必要的上下文，不会超限。

## 五、可行性评估

### 5.1 理论可行性

| 维度 | 评估 | 说明 |
|------|------|------|
| **技术可行性** | ✅ 完全可行 | aikota 已有完整架构，只需正确配置 |
| **信息完整性** | ⚠️ 有损 | 压缩会丢失细节，但可通过 Memory Search 补救 |
| **连续性** | ✅ 支持跨会话 | checkpoint 机制保证会话延续 |
| **性能** | ⚠️ 需权衡 | 长会话需要更多压缩操作 |

### 5.2 实际限制

1. **压缩质量**：LLM 生成的摘要可能丢失细节
   - 解决方案：结合 Memory System 的全文搜索
   
2. **摘要膨胀**：多次压缩后摘要可能增长
   - 解决方案：定期重新压缩（已有机制）

3. **模型上下文限制**：即使压缩，单次请求仍有上限
   - 解决方案：动态调整阈值，确保不超限

## 六、操作建议

### 方案 A：最小改动（推荐）

只需在 `config.toml` 中启用：

```toml
[memory]
enabled = true

[checkpoint]
thresholds = ["50%", "70%", "90%"]
reserved = 16384
```

### 方案 B：完全无限（激进）

```toml
[memory]
enabled = true
reconcile_on_search = true  # 搜索前自动重建索引

[checkpoint]
thresholds = ["30%", "50%", "70%", "90%"]  # 更频繁压缩
reserved = 8192  # 更多空间给摘要
keep_recent = 40000  # 保留更多近期上下文
```

### 方案 C：禁用压缩（不推荐）

```toml
[checkpoint]
enabled = false  # 不推荐：会导致上下文超限
```

## 八、结论

### 8.1 核心结论

**aikota 已经具备"无限上下文"的能力，但需要正确配置。**

通过启用 `memory.enabled = true` 和配置 `[checkpoint]`，aikota 可以：

1. 自动压缩超长上下文
2. 持久化压缩结果到磁盘
3. 跨会话恢复完整上下文
4. 通过 Memory Search 补充细节

### 8.2 第一性原理总结

| 原则 | 应用 |
|------|------|
| **信息不灭** | 原始对话保存在磁盘，压缩只是摘要 |
| **按需加载** | 每次只加载必要上下文，避免超限 |
| **渐进式压缩** | 多次阈值触发，逐步折叠历史 |
| **可回溯** | Memory System 允许查找历史细节 |
